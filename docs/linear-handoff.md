# Контракт передачі

Одна канонічна Task ID → одна задача Linear. Ключ відповідності: workspace + team + project + source_project_key + Task ID. Назва не є унікальним ключем.

Опис містить весь source task text: контекст, scope, implementation notes, AC, edge cases, out of scope, dependencies, references, milestone/module, scope status, O/M/P/E і labels. Не скорочувати до одного речення. Позначки Requires Tech Lead validation зберігати дослівно. Інженерні припущення не перетворювати на підтверджені вимоги.

Milestone/module спершу зберігати в описі. Створення project milestones, додаткових labels, призначення людей, циклів чи дат потребує відповідного scope запиту. Не створювати окремі FE/BE задачі з одного multi-workstream рядка: це змінить канон.

## Перед записом

1. Отримати реальні team/project/state/label IDs доступним connector. Не вигадувати UUID або Linear issue IDs. Якщо призначення неоднозначне — уточнити його, продовжуючи локальну підготовку.
2. Завершити semantic review; unresolved blockers не публікувати як ready. DRAFT можна передати лише як явно запитаний backlog draft. Не перетворювати conditional reserves на підтверджений scope.
3. Знайти існуючі задачі в точному destination за ключем джерела. Перевірити pagination. Побудувати create/update/unchanged/conflict план; кілька збігів → conflict.
4. Зберегти конкретний план, source SHA-256, content hashes і результат review локально. Якщо користувач уже доручив публікацію цього набору, виконати; інакше показати пакет і запросити дозвіл саме на запис.

## Запис і відновлення

Публікувати послідовно. Після кожної успішної операції записувати Task ID, реальний issue ID/URL, content hash і destination у `sync-state.json`. При зміненому destination попередні відповідності непридатні. Оновлення не має перезаписувати чужі поля чи ручні правки: порівняти remote з останнім синхронізованим станом, conflict винести на розгляд.

Спочатку створити всі дозволені задачі, потім додати blocking relations за їх реальними IDs. Текст Dependencies не означає автоматично blocking relationship: використовувати тільки явно позначені зв’язки: Blocking означає поточна задача блокує вказану; Blocked by означає вказана задача блокує поточну. Джерело напрямку — sections["Залежності"], а не плоский dependency_task_ids (це лише індекс перевірки існування IDs). Дедуплікувати однакові directed edges, записані з обох боків. Невідомі/циклічні залежності винести у review.

При timeout не повторювати create наосліп: перевірити remote за ключем і reconciliation-журналом. Якщо результат неможливо встановити — зупинити цей запис. При auth/error зберегти прогрес і повідомити точну причину. Не видаляти remote задачі як спосіб виправлення.

Після запису прочитати створені задачі й звірити описи, labels та зв’язки. Фінальний звіт: created/updated/unchanged/blocked, посилання й незавершені дії. Без живого доступу результат називається тільки локальним draft.
